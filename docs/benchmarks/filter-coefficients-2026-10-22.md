# Live filter-coefficient cache component screen

This isolated pure Java prototype caches two parameter-only expressions in the standard filter block: `k * (1 - t1 / t2)` and `k * t1`. Before reuse it compares raw bits of all three live parameters, including signed zero. Parameters that change through existing field access trigger recalculation. Exact standard blocks use the cache; subclasses retain the original virtual getter operations and their order. The generic first-order filter kernel uses the same state coefficient. Multiplication, subtraction and division order in the output and derivative equations remain unchanged; no reciprocal substitution or state/output cache is introduced.

The component result does not support a full simulation timing sweep or production promotion. Control median is 0.0039836 seconds and candidate median is 0.0041561 seconds per 640,000-update batch. The median paired saving is -0.0002503 seconds, with 2/7 candidate wins. Batches are only about four milliseconds, so these figures are a screening result, not a precise complete-runtime estimate. The extra cache checks are a possible contributor to the loss; their exclusive cost was not measured.

The probe performs 387,044 scalar comparisons across the three limiter types. It compares stored input, state, retained derivative, output, scratch arrays where used and equation residuals for alternating direct Euler and kernel updates. Random live parameter changes, external state restoration, zero/nonzero steps, signed zero, subnormal, large and nonfinite values are covered. A custom subclass verifies getter-call order while the property is enabled and disabled. Comparisons canonicalize NaNs rather than checking payload identity. These are scalar assertions, not 387,044 separate model fixtures or independent reference comparisons.

The timing fixture uses 64 standard filter blocks, 10,000 passes per batch, 32 alternating warmup batches and seven order-alternating measured pairs in one JVM pinned to one logical CPU. Parameters remain constant during each timed batch; every batch begins with restored zero input/state/derivative and consumes the same deterministic input sequence. All checksum values are identical. Both arms retain the candidate-capable class; the control disables coefficient reuse. The component does not reproduce the full controller graph, its mixture of block types, or solver call sites.

No complete simulation is run for this candidate. Therefore this report makes no claim about Case 1/2 timing, full-recording equality, independent-reference accuracy or the eight-second objective. Production source and supplied references are unchanged. The full objective remains open.

Original and candidate sources, compiled classes, probe, commands, affinity, checks, raw timings and runtime identities are retained. The retained CML kernel source hash is checked against the classpath's existing compatibility build before modification. The result rules out assuming that a cache checked on every numerical read is a useful controller optimization; any further parameter reuse needs a distinct lifecycle design and its own validation.
